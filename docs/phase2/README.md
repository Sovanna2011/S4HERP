Everything below was run, not assumed. `db/tests/integrity-rules.sql` asserts the
**specific** error each rule should produce — a test that merely "threw
something" is not a pass, because a misconfigured harness throws too.


Run it against a running stack with:

```bash
docker compose exec -T db /opt/mssql-tools18/bin/sqlcmd \
  -C -I -S localhost -U sa -P "$MSSQL_SA_PASSWORD" -d S4HERP \
  -i /path/to/db/tests/integrity-rules.sql
```

`-I` matters: `sqlcmd` defaults `QUOTED_IDENTIFIER` to OFF, and any DML against a
filtered index fails without it. Getting this wrong makes every test "pass" for
the wrong reason.

The whole pipeline was also run from an **empty volume** — migration, five
scripts, seed, readiness — to confirm it is reproducible rather than an artefact
of an incrementally built database.

## Decisions taken in this phase

Argued in [docs/adr/016-018](../adr/016-018-phase2-decisions.md):

- **ADR-16** — one `DbContext`, not one per module, so the atomic cross-module
  posting transaction is the default rather than per-call-site work.
- **ADR-17** — `Organization.Domain` is an explicit shared kernel; the
  architecture-test rule is amended accordingly.
- **ADR-18** — `fin.JournalEntryLine` carries no foreign keys on its dimension
  columns; the posting engine validates and a reconciliation job verifies.

And one **correction to the blueprint**: the formatted document number must carry
the company code. Seeding the intercompany pair produced two documents numbered
700000001 in different company codes — correct behaviour — which collided on a
tenant-wide unique index. Now `KSS-1000-2026-IC-0700000001`, unique per company
code.

## Assumptions taken

Five of the six [open questions](../blueprint/README.md#open-questions) were not
answered before this phase started. None of them blocks the schema, so each was
assumed rather than waited on:

| Question | Assumption taken | If the answer differs |
| --- | --- | --- |
| Tenancy | Shared database, `TenantId` + RLS | Schema is identical for database-per-tenant; only connection routing changes |
| Gapless numbering | `NumberRange.IsGapless` defaults true, per range | Flip the flag per document type; no schema change |
| Parallel ledgers | `LedgerId` on every line; seeded leading + IFRS | Add ledger rows; no schema change |
| Khmer collation | Database default, `NVARCHAR` throughout | A collation change is a rebuild — **decide before go-live** |
| SAPUI5 licence | Not relevant to Phase 2 | Affects Phase 4 only |

The sixth — deleting the `Products` sample — is done.

## Limitations

Stated plainly, because a phase report that lists only what worked is not a
report:

1. **No posting engine.** Journal rows were seeded directly. Period checks, field
   status, tax calculation, CO derivation, number allocation, balancing and
   idempotency are Phase 3. The database enforces balancing *after* the fact; it
   does not yet prevent an unbalanced document from being attempted.
2. **`wf`, `rpt` and `intg` are empty.** Workflow, Reporting and Integration have
   schemas but no tables.
3. **Assets are not modelled.** `JournalEntryLine.AssetId` exists and the
   reconciliation account type is supported, but the asset master, depreciation
   areas and depreciation runs are Phase 3.
4. **The Data Dictionary (`cfg.Dictionary*`) is not built.** SE11 and SE16N
   depend on it; both are Phase 3 alongside the metadata generator that will
   populate it from the EF model.
5. **Partitioning covers `fin.JournalEntryLine` only.**
   `fin.JournalEntryHeader` and `audit.AuditLog` also warrant it, but their
   clustered keys do not currently carry a partition column — the header's unique
   index would have to take `FiscalYear`, and `AuditLog` needs a persisted year
   column. Both are key changes and belong in a reviewed migration, not a startup
   script. `db/scripts/030-partitioning.sql` says so and refuses to act on a
   populated table.
6. **No columnstore index yet.** Correctly deferred until reporting volume is
   measurable — it costs insert throughput on a latency-sensitive path.
7. **The read-only login is created only if it already exists at server level.**
   `040-readonly-login.sql` grants and denies, but will not mint a login with a
   hard-coded password from application code. Provisioning creates it.
8. **Migrations still run at startup.** Right for development, wrong for a
   cluster where replicas would race. Phase 5 splits deployment-time migration.
9. **No authentication.** Every request runs as the system principal, so RLS is
   exercised but not yet driven by a real user. Phase 3.
